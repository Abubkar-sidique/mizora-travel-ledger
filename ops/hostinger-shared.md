# Hostinger Web/Cloud shared hosting: migration and deployment gate

## Status

**This guide is not authorization to deploy or cut over production.** The code now has an opt-in PDO MariaDB driver, a versioned InnoDB schema, a read-only SQLite importer, account-row locking for concurrent allocations, application-maintained chat counters, and a logical SQL backup path. SQLite remains the default local driver.

The current local schema is MariaDB schema version 1; upgrades are intentionally refused until a separately reviewed additive migration exists. Hostinger's import guidance disallows imported triggers and procedures. The port uses enforced MariaDB CHECK/foreign-key constraints plus server-side application validation and transaction locks. The automated migration/security/concurrency/backup/browser suite passed against MariaDB 11.4.10; MariaDB 10.5 has not been integration-tested. MariaDB's published lifecycle lists community 10.5 maintenance ending June 24, 2025, so an actual 10.5 service in 2026 is a security-support blocker unless Hostinger confirms an applicable maintained/extended-support path. [MariaDB Server lifecycle](https://mariadb.org/about/). Production status is **NO-GO until the database version/support status, actual account configuration, and owner-approved acceptance are verified**.

## SQLite-to-MariaDB import and cutover

1. Back up the SQLite DB with the existing SQLite backup tool, verify that backup, and keep the original DB and any WAL/SHM files untouched. Stop all source writes before the final import.
2. In hPanel create a separate, empty MariaDB database. If importing from a workstation, temporarily allowlist only that workstation's IP under **Remote MySQL**. Remote MySQL availability and TLS CA details must be confirmed in the account.
3. On a private machine with PHP SQLite3 and PDO MySQL enabled, set `LEDGER_DRIVER=mysql`, `LEDGER_DB_HOST`, `LEDGER_DB_NAME`, `LEDGER_DB_USER`, and `LEDGER_DB_PASSWORD` to the new target. Set `LEDGER_DB_SSL_CA` to the verified provider CA for a remote connection. Run `php ops/migrate-sqlite-to-mariadb.php --source=/private/ledger.sqlite --confirm-empty-target`.
4. The importer opens SQLite read-only and requires schema v7, SQLite integrity, clean foreign keys, and valid financial/reference/allocation rules. It creates MariaDB schema v1, refuses any target with data, imports explicit IDs in dependency order inside an InnoDB transaction, and compares every source row hash, table count, and each account's opening/debit/credit/closing totals before commit. A failed import rolls back its data transaction; the source file is never written or removed. A successful target is not a cutover.
5. Run the MariaDB HTTP/browser/security/concurrency suite against a disposable imported copy. Verify tenant separation, CSRF/XSS, login rate limits, payment allocation races, export totals, and backup restore into a separate empty database. Run the same SQLite suite to ensure local development remains supported.
6. Keep the original SQLite source offline/read-only until the target passes acceptance and the owner approves cutover. Rollback means switch to the preserved source before target-only writes; after MariaDB writes begin, reconcile them before rollback. No cutover is performed by this code.

## hPanel deployment sequence (after the code migration passes)

1. In **Websites → Dashboard**, confirm the site is a Web or Cloud custom PHP website, attach the intended domain, and install SSL. Verify HTTPS works before enabling production cookies.
2. In **Databases → Management**, select the correct website and create a new database/user. Save the exact database name, username, password, and host from hPanel in a private password manager. Each database has one user. Use a generated hex password if setting credentials through `SetEnv` directives in `.htaccess`; `.htaccess` is not served as a normal file, but verify direct access is denied. Never commit the credentials.
3. In **PHP Configuration**, select a supported PHP version and confirm `pdo_mysql`, `zip`, and session support. Confirm the PHP version actually applied to this website/subdomain. Do not publish `phpinfo()` as a diagnostic endpoint.
4. Create a private PHP session directory outside `public_html` if the account permits it. Configure the `LEDGER_*` settings through the site's supported environment mechanism; if the only option is `.htaccess`, verify the server passes `SetEnv` values to PHP and that a request to `/.htaccess` is denied. Use the actual hPanel database host, which may differ from `localhost`.
5. Build the allowlisted release ZIP locally. It must contain application files and deployment instructions only; exclude SQLite databases, backups, test fixtures, and secrets. Verify the manifest/hash before upload. Upload/extract into a new release folder, then point the domain document root to its `ledger` directory if hPanel permits; otherwise use the reviewed `.htaccess` rules and keep operational files outside `public_html`.
6. Before uploading the app, run `ops/migrate-sqlite-to-mariadb.php` from a private migration workstation against the new empty target using a secured connection. The importer is intentionally excluded from the public release ZIP and requires a reachable MariaDB endpoint. If Remote MySQL is unavailable, stop and have Hostinger confirm an approved secure migration route (for example, an account-side CLI workflow); this release does not generate a phpMyAdmin-ready SQLite export. Do not paste the database password into an untrusted tool. No cutover is performed by this guide.
7. Configure the private MariaDB connection and a private PHP session path using the supported account features. Apply the least-permissive file modes available through hPanel/File Manager. Verify direct requests to database, configuration, backup, test, and internal PHP paths are denied.
8. Smoke-test login, tenant isolation, CSRF, account pages, debit/credit, allocations, voids, reports, CSV/XLSX/print, and backup/restore on the target website using test accounts/data. Inspect HTTPS cookies and PHP/database errors without exposing secrets.
9. Configure and test scheduled off-site database backups using a method available on the plan, such as a supported cron job. Restore a downloaded `.sql` backup into a separate empty test database and compare counts/balances before approving cutover. [Hostinger cron setup](https://support.hostinger.com/en/articles/1583465-how-to-set-up-a-cron-job-at-hostinger)
10. Keep the SQLite source untouched and retain a rollback window. Production activation and acceptance remain owner decisions; this repository does not deploy or change production data.
